## 1. Что это

Сеть, где владельцы обычных компьютеров считают одну модель вместе. Плоскость
управления принимает запросы по OpenAI-совместимому API, ставит их в очередь и
собирает ответ. Модель, которая не влезает в одну видеокарту, делится по слоям.
Пока компьютер один, он считает модель целиком через Ollama. Подробности —
в [`how-it-works.md`](how-it-works.md).

## 4. Что ещё не сделано

Список на 2026-11-07. Замеры из прежней редакции этого раздела сохранены в §3
и в архиве; сюда они не копируются второй раз.

1. **Первый запуск группы всё ещё гонит тензоры от ведущего.** Кэш стадии (`-c`)
   делает это один раз, но отдача домашнего канала измерена как 1,4–1,5 МБ/с.

3. **Колонка версии в панели пишется при регистрации**, а не при heartbeat.
   Повторные нажатия «подключиться» оставляют несколько строк одного компьютера.
4. **Панель**: нет страницы «мой вклад», exe не подписан.
5. **Нет второй площадки** плоскости управления и нет протокола `/v1/messages`.
6. **RAG заморожен**: документы и страница есть, корпуса и потребителя нет.
7. **Карты ниже 8 ГБ и карты не NVIDIA не измерялись.** Программа смотрит только `nvidia-smi`.

## 5. Что уже закрыто и что открыто

Пункты про Python-пайплайн закрыты как исследование и в продукт не вошли.
Скорость GPT-OSS-20B на этой машине даёт llama.cpp: холодный декод 6.07 tok/s,
ответ чата «Paris». GPT-OSS-120B не запускался.

Сейчас закрыто другое: платформа сама назначает диапазоны `gpt-oss:20b`,
программа участника сама ставит llama.cpp b12167 и сама отвечает моделью,
которая уже в памяти. Сборка 0.3.6 оставляет группу слоёв обычным путём.
Целиком модель считает только компьютер, который сам сообщил, что файл
помещается на его карту. На сборщике ответа включены черновик `ngram-mod`
и квантование KV-кэша.

Открытым остаётся замер: один и тот же короткий запрос на живой группе
без черновика и с `ngram-mod`. Пока этого прогона нет, ускорение не записано.
Если пачка не быстрее текущего режима, черновик нужно выключить. Пункт 1
из §4 тоже открыт: при холодном старте тензоры всё ещё идут от ведущего.
Своего замера пути без этой передачи нет, скорость для него не записывается.

### Что оставить из второго разбора, 2026-11-07

Это разбор кода, не замер. Чисел tok/s из него в журнал не переносим.

Пачка черновиков платит за переход один раз на несколько токенов. На канале
1,4–1,5 МБ/с пачка ещё и тяжелее одного токена: выигрыш есть только если
принятых токенов хватает и на задержку, и на лишние байты. `ngram-mod` ищет
дословный повтор, поэтому на свежем тексте он может не ускорить ответ.
Голова EAGLE в коде есть только для `gpt-oss:20b`; у модели без этого файла
остаётся ngram. Размер пачки код не задаёт, его выбирает сборка b12167.
Долю принятых черновиков программа участника из лога llama-server не читает:
три числа будущего прогона придётся снять в момент запуска.

Квантование KV-кэша к скорости канала не относится. На локальном прогоне оно
удерживало окно на карте: 70,6 tok/s против 29,9, когда кэш уезжал в процессор.

Координатором становится узел с наименьшим идентификатором. `rtt_ms` в
heartbeat — задержка до плоскости управления, не между участниками. Туннель
сводит RPC на этой плоскости, потому что порт стадии наружу не открывается.
Прямой путь между близкими участниками и выбор соседа по близости могут
значить больше черновика, но это отдельное решение: у текущего туннеля есть
причина, его не выключают флагом.

Прогон «координатор на видеокарте, стадия на процессоре той же машины, переход
через туннель» не заменяет два дома. Старое локальное число 12,1 tok/s этим
каналом не является. Живой ответ по-прежнему даёт одна и та же короткая фраза
на двух физических компьютерах: без черновика, с ngram и, для gpt-oss, с его
головой. Пока пачка не быстрее, головы для других моделей не добавляем.

### Что оставить из третьего разбора, 2026-11-07

Тоже разбор, не замер. Речь о коммите `3029e1a`.

Выигрыш пачки есть только если принятые токены окупают и обычный шаг, и
черновик, и проверку. В проверку входят вычисления, ожидание сети и байты
пачки. Квантование KV-кэша — тип кэша на карте, не сжатие активаций, которые
идут между участниками.

Непрерывный конвейер FlowSpec, SpecPipe и PipeInfer — другое направление, не
флаг 0.3.6. Пока предсказание верно, стадии одного ответа работают одновременно
и частично прячут задержку за работой. Промах откатывает ветвь. Широкое дерево
увеличивает трафик, на 1,4–1,5 МБ/с это может съесть выигрыш. Первый токен всё
равно проходит всю модель. Готовые реализации опираются на голову конкретной
модели; SpecPipe мерили на 10 GbE, не на домашней отдаче. В репозитории этого
конвейера нет, одним флагом он не включается. Строить его до прогона обычной
пачки не нужно: если пачка не быстрее режима без черновика, спекуляцию для
этой конфигурации выключаем.

Перед тем прогоном поправить два дефекта, иначе сравнение будет ложным.
`draftSpecArgs` при отсутствии файла головы всегда ставит ngram, даже если
просили другой режим или выключение. `meshConfigKey` не включает тип черновика
и путь к голове, поэтому смена режима может не перезапустить уже работающий
`llama-server`. Проверку пачки не считать одним RTT, пока это не видно в логе
llama.cpp: RPC b12167 делает отдельные операции над тензорами. Диапазоны слоёв
в топологии не передаются процессу как `--tensor-split`; автоматический план
пишет их в heartbeat, а фактическую раскладку надо читать из журнала загрузки.
`wall_ms` начинается после того, как рантайм уже принял HTTP-запрос, и не
заменяет время до первого токена у клиента. Чужой файл головы вместо уже
закреплённого `eagle3-gpt-oss-20b-Q8_0.gguf` без своего прогона не подключать.

### Прогон трёх режимов, 2026-11-07

Сборка 0.3.7 различает `none`, `ngram-mod` и `draft-eagle3`. Пропавший файл
головы больше не подменяется ngram. Смена режима входит в отпечаток запуска,
и `llama-server` перезапускается. Переменная `COMPUTE_SPEC_TYPE` выбирает
режим на время прогона. В документации сборки b12167 доля принятых черновиков
печатается строкой `draft acceptance rate` как `accepted / generated`. Своего
лога с этой строкой нет.

Прогон 2026-11-07, 23:11–23:45 по местному времени, одна и та же короткая фраза,
сборка 0.3.7 на обоих компьютерах. Группа была собрана: этот компьютер вёл
слои 0–11, второй держал 12–23. Старый узел с `qwen3:8b` в группу не входил.

Три режима подряд, каждый со своим перезапуском программы:

| Режим | Токены клиенту | Время до первого токена | Итог |
| --- | --- | --- | --- |
| `none` | 0 | нет | обрыв через 660 с |
| `ngram-mod` | 0 | нет | обрыв через 660 с |
| `draft-eagle3` | 0 | нет | обрыв через 660 с |

tok/s нет. Строки `draft acceptance rate` в журнале llama.cpp нет. Строк

всё это время оставалась около 2,7–3,1 ГБ. Задание забиралось примерно через
секунду после старта, раньше, чем узел успевал получить план группы.

С 00:06 до 07:50 программа поднимала llama.cpp снова и снова. Каждый раз
пять или сорок пять минут не было ни строки вывода, затем процесс
останавливался. Причина на сервере: туннель отвечал `403 mixed_owners`.
Два компьютера были заведены разными аккаунтами, и платформа не пропускала
между ними байты модели. Сборка 0.3.8 это меняет: чужой компьютер может
держать слои и принимать байты вычисления, но задание, текст и место ведущего
остаются у компьютера, с которого отправлен чат. Общий аккаунт для этого не
нужен. Запись второго компьютера в аккаунт первого снята. Ручная группа из
разных владельцев по-прежнему не открывает туннель.

Решение по правилу прогона не принимается: таймаут — не скорость. Ни один
режим не объявлен быстрее, спекуляция не выключается. По умолчанию файл головы
включает `draft-eagle3`, а без файла и без явного режима остаётся `ngram-mod`.
Непрерывный конвейер не начинается.

### Замечания по безопасности, 2026-11-07

Разбор кода 0.3.7, коммит `1875ba3`, без запуска. Вредоносного не найдено.
Плоскость управления, панель и программа Windows целиком не проверялись.

До приглашения людей на машины с их данными закрыть три вещи. Обновление
скачивается с того же сервера, который отдаёт хеш, подписи нет: на Windows
программа ставит новую сборку сама. Служба Linux запускается от root, в unit
нет отдельного пользователя и ограничений. `ggml-rpc-server` без TLS принимает
байты, которые плоскость управления перекладывает из туннеля. Автоматическая
группа пускает чужой компьютер только стадией. Ручная группа из разных
владельцев туннель не открывает: чужой компьютер нельзя назначить ведущим.

Ещё два поведения бьют по машине, где Ollama уже занята не только сетью.
`setup` на Linux пишет квантование KV в службу Ollama и перезапускает её.
Перед группой слоёв выгружаются все модели, которые Ollama держит в памяти, а
не только модель сети. Установщик Ollama качается без зашитого хеша, в отличие
от llama.cpp. Текст обычного чата остаётся `private` и уходит только на узел
того же владельца. `shared` отдаёт текст другому участнику, и это должно быть
видно при подключении, не только в документации.

## 5.1. Что сеть обещает и чего не обещает (2026-11-09)

Это итог разбора на трёх участниках в разных городах. Числа — где замер, где
расчёт, сказано прямо.

| Обещание | Статус | Чем ограничено |
|---|---|---|
| Чат моделью, которая влезает в одну карту | **работает**, локальная скорость (замер: 67,5 tok/s на 8 ГБ) | диск и канал участника |
| Модель больше одной карты, машины в **одной локальной сети** | класс `lan`: работает, замер на одной машине 12,1 tok/s | в локальной сети между двумя машинами не замерялось |
| Модель больше одной карты, машины в **разных городах** | медленный класс; расчёт для 41 ГБ и RTT 55/114 мс: **2–3 tok/s** | задержка перехода на каждый токен и отдача 1,4–1,5 МБ/с при первом заполнении |
| Много одновременных ответов | масштабируется репликами и конвейером | не скоростью одного ответа |
| Один ответ быстрее от новых участников | **нет** | токен проходит стадии по порядку, каждая стадия добавляет переход |

Практический вывод, который стоит держать в голове при наборе участников:
**человек с двумя и больше компьютерами в одной сети даёт и ёмкость, и
скорость; одиночная машина в другом городе даёт только ёмкость.** Это не
недоработка, а свойство линка, и от него зависит, кого звать в сеть.

### Проверка, влезает ли модель в группу

Добавлено `internal/store/layersplit_fit.go` — `PlanGroupFit`. Считает
необходимую память (веса плюс KV-кэш на заданное окно), полезную ёмкость карт
(минус 1,5 ГиБ запаса на рабочем столе) и недостачу в слоях и байтах, чтобы
отказ звучал числами, а не `cudaMalloc failed`.

Тесты на реальных числах (`layersplit_fit_test.go`): модель 41 ГиБ и карты
8+16+16 ГиБ дают отказ с недостачей; четыре карты по 16 ГиБ — согласие; KV-кэш
учитывается; неизвестный объём карты не превращается в ложный отказ.

**Проверка подключена к раскладке** (2026-11-09). `EnsureLayerSplit` берёт размер
модели из ревизии, а если поля нет — из суммы файлов каталога, считает
`PlanGroupFit` по ёмкости всех участников и, если не влезает, не создаёт группу:
переводит прежние автоматические группы в `draining` и записывает топологию в
статусе `failed` с текстом причины (миграция `0024_topology_error.sql`, колонка
`topologies.error`). Панель показывает этот текст рядом со статусом.

Проверено на живой сети: для `qwen2.5:72b-instruct-q4_0` при картах 8+12+12 ГиБ
запись появилась сразу после heartbeat —

```
модель qwen2.5:72b-instruct-q4_0 не помещается в группу компьютеров:
не хватает 24 слоёв (11.5 ГиБ): нужно 38.4 ГиБ, есть 26.9 ГиБ
```

то есть вместо `cudaMalloc failed` участник и панель видят, чего именно не хватает.

**Причина доходит и до участника.** Плоскость управления отдаёт её в ответе
heartbeat (`mesh_fit`), программа пишет в свой журнал одну строку при изменении
причины и показывает её в окне: «группа слоёв не поднимается: …». Проверено на
живом узле (сборка 0.3.21, локальная, в релизный фид не выложена):

```
WARN shard group cannot start reason="модель qwen2.5:72b-instruct-q4_0 не
помещается в группу компьютеров: не хватает 24 слоёв (11.5 ГиБ):
нужно 38.4 ГиБ, есть 27.4 ГиБ"
```

Открытым остаётся публикация 0.3.21 в релизный фид: сейчас фид отдаёт 0.3.20,
поэтому остальные участники получат эту строку только после выкладки сборки.

## 6. Целевые модели

Модель, которую код режет сегодня, — `gpt-oss:20b` (24 слоя). Таблица ниже —
кандидаты, а не то, что уже запущено. GPT-OSS-120B не запускался.

Критерии отбора — не размер, а: лицензия, позволяющая хостить и раздавать веса;
архитектура, которую рантайм умеет резать; разреженность (MoE) для ёмкости.

### Флагман для шардирования: MoE, не dense

| Модель | Актив / всего | Лицензия | Зачем |
|---|---|---|---|
| **GPT-OSS-120B** | 5.1B / 117B | Apache 2.0 | родной MXFP4 ≈ 63 ГБ на всю сеть; узел считает как 5B — **цель для демо** |
| Qwen3.5-122B-A10B | 10B / 122B | Apache 2.0 | 256K контекст, 201 язык, мультимодал |
| Qwen3-Coder-Next 80B-A3B | 3B / 80B | Apache 2.0 | SWE-bench 70.6 при 3B активных: кодинг почти бесплатен по вычислениям |
| Step-3.5-Flash | 11B / 196B | Apache 2.0 | MTP-3 из коробки (1.5–3× декод), 350 tok/s |
| GLM-4.5-Air | 12B / 106B | MIT | сильная математика, дешёвая лицензия |

### Dense-класс (проще всего для нашего рантайма)

| Модель | Размер | Лицензия | Роль |
|---|---|---|---|
| Qwen3.5-9B | 9B | Apache 2.0 | замена `qwen3:8b` в быстром классе |
| Llama 3.3 70B | 70B | Llama Community (EU ok) | понятная демонстрация «не влезает в одну карту» |
| QwQ-32B / R1-Distill-32B | 32B | Apache 2.0 / MIT | рассуждения, 2 узла |
| Muse-Glimmer-30B | 30B | Apache 2.0 | агентный кодинг на потребительском железе |

### Чего избегать

- **Llama 4 / Llama 3.2 Vision** — лицензия исключает ЕС для мультимодальных.
- **Mistral Medium 3.5, MiniMax** — Modified MIT с потолками выручки/MAU: модель
  «подорожает» ровно тогда, когда сеть вырастет.
- **DeepSeek-V4-Flash 284B** — MIT и 1M контекст, но Q4 ≈ 156 ГБ: рано.
- **Гибридные архитектуры** (Qwen3.8-27B, Ling, Kimi-Linear, Nemotron) — нужен
  перенос рекуррентного состояния вместо KV-кэша; вторая версия рантайма.

### Несколько моделей одновременно

Платформа уже маршрутизирует задания по `served_model` каждого узла, поэтому
разные узлы могут держать разные модели. Не хватает **пулов**:

| Класс | Как обслуживается | Пример |
|---|---|---|
| `fast` | реплики на одиночных узлах | Qwen3.5-9B |
| `capacity` | шард-группа (топология) | GPT-OSS-120B |
| `code` | отдельный пул | Qwen3-Coder-Next 80B-A3B |
| `embed` | мелкий пул (уже есть) | nomic-embed-text |

Для пулов нужны: учёт ресурсов при вступлении узла (VRAM/RAM уже в heartbeat),
прогрев по спросу и вытеснение по популярности. Ограничение: каждая модель —
это диск и трафик участника, поэтому каталог должен оставаться маленьким
(4–6 моделей).

## 8. Грабли, которые уже стоили времени

| Грабля | Что делать |
|---|---|
| Сборка падает с OOM | `GOMAXPROCS=2`, `go build -p 1`, при нужде остановить узел и `ollama stop qwen3:8b` (лимит commit ~31 ГБ) |
| KV-кэш 16K на 8 ГБ не влезает рядом с рабочим столом | `OLLAMA_KV_CACHE_TYPE=q4_0` на картах ≤ 9 ГБ (установщик выбирает сам) |
| Два параллельных запроса поднимают два llama-server и оба падают | `OLLAMA_NUM_PARALLEL=1` |
| Порт 18081 занимает Ollama (её собственный llama-server) | проверять порт перед стартом шард-группы |
| TCP-опрос `ggml-rpc-server` рвёт активную RPC-сессию | стадию проверять только по живости процесса, порт опрашивать лишь у координатора |
| `client_max_body_size 16m` в nginx обрезает поток туннеля | отдельный `location` с `client_max_body_size 0` |
| Выкладка gateway: забыл `chmod 0755` | 203/EXEC и сервис лежит; после `mv` всегда `chmod`, затем `systemctl reset-failed` |
| Файлы конфигов узла с BOM | писать JSON через `UTF8Encoding($false)`, иначе `parse config: invalid character` |
| PowerShell ломает кавычки в командах для SSH | писать `.sh` файл и запускать через `tools/ssh_put.py` + `bash` |

## 10. Договорённости

   быть видно в выводе инструмента.

   `nginx`, `postgresql` — `active`.

   упирается в домашнюю отдачу 1,4–1,5 МБ/с. Своего замера «уложилось в минуты» нет.
