# ADR 0003 — Сетевая идентичность: домены, VPN и переезд сервера

- **Статус:** accepted (принципы), требует выбора конкретного домена и решения по VPS-точке входа
- **Дата:** 2026-11-05
- **Контекст:** сервер физически переезжает в другой город; внешний IP изменится; возможен CGNAT у нового провайдера. Платформа ещё не реализована — значит требования можно заложить сразу, а не латать потом.

## 1. Решение: никакой компонент не знает IP управляющего узла

Жёсткое правило проекта:

1. Внешние клиенты (Harness, Android, SDK, веб-панель) обращаются к `https://api.<domain>/v1` и `https://panel.<domain>`.
2. Worker Agent при запуске получает **enrollment URL** и далее держит **исходящее** соединение к `control.<domain>:443`. IP не хранится в конфиге агента, а разрешается через DNS при каждом переподключении.
3. Внутренние адреса (`192.168.10.60`, `10.10.0.1` и т.п.) существуют только внутри площадки и никогда не попадают в клиентские конфиги, в документацию API и в манифесты моделей.
4. Любой конфиг, который пришлось бы менять при смене IP, считается дефектом архитектуры.

## 2. Решение: транспорт до управляющего узла — исходящий туннель

| Сценарий | Как работает | Следствие для переезда |
|---|---|---|
| Провайдер даёт публичный IPv4 | DNS A-запись → IP, порт-форвард 443 на `192.168.10.60` | меняется только A-запись |
| CGNAT, публичного IPv4 нет | домашний сервер сам поднимает WireGuard-туннель к VPS с постоянным IP; VPS проксирует 443 → туннель | IP домашнего сервера **вообще не важен**, туннель восстанавливается сам |
| Промежуточный вариант | Cloudflare Tunnel / аналог: исходящее соединение, публикация по домену | IP не важен, но добавляется зависимость от третьей стороны |

Рекомендация: **держать оба пути** — публичный IPv4 как основной, WireGuard-туннель на VPS как резервный. Это дешёвая страховка: VPS 1 vCPU/1 GB стоит копейки и снимает целый класс проблем.

WireGuard настраивается с `PersistentKeepalive = 25` и допускает смену endpoint: сторона, которая инициирует соединение (домашний сервер), может переехать на любой IP, пир просто обновит endpoint по последнему валидному пакету.

## 3. Решение: DNS и сертификаты

- Домен и поддомены: `api.`, `panel.`, `control.` — обязательны.
- **TTL заранее снижается до 300 секунд** (за 1–2 суток до переезда), иначе часть клиентов будет ходить на старый IP до истечения прежнего TTL (может быть часы и сутки).
- Сертификаты Let's Encrypt выпускаются **через DNS-01**, а не HTTP-01: DNS-01 не зависит от доступности сервера по IP и продолжает работать в момент переезда. Сертификат привязан к домену, поэтому сам по себе смена IP его не ломает — ломает только невозможность продления.
- `hostname` и `known_hosts` у клиентов не связаны с IP; при смене IP SSH host keys остаются те же, предупреждений не будет.

## 4. Решение: переживание простоя

Переезд — это плановый простой, и система должна его переживать, а не «падать красиво».

- **Maintenance mode** в Control Plane: прекращает выдачу новых lease, текущие задания либо доводятся, либо возвращаются в очередь с идемпотентным `task_id`.
- **Lease TTL + heartbeat**: если Worker не получает управляющий узел, он не теряет себя — переходит в `disconnected`, повторяет подключение с экспоненциальной задержкой (1→2→5→15→30→60 с, потолок 5 мин) без ручного вмешательства.
- **Состояние задач — в БД**, а не в памяти процесса: после старта Control Plane очередь восстанавливается из JetStream.
- **Кэш весов на Worker не удаляется** при потере связи: узел может продолжать обслуживать уже загруженные модели локально.
- **RPO**: PostgreSQL — ежедневный `pg_dump` + WAL-архив (после Этапа 1); конфиги VM/CT — `vzdump` (уже включён для CT 101); ключи/секреты — отдельный бэкап вне сервера.
- **RTO**: управляющий узел поднимается из бэкапа на новом месте за 15–30 минут, если бэкап свежий и проверенный.

## 5. Чего не избежать при переезде

Это не про DNS, а про физику:

1. **Локальный IP хоста.** `vmbr0` имеет статический `192.168.10.50/24`. Если в новом месте роутер раздаёт другую подсеть (что вероятно), адрес нужно поменять **с локальной консоли** — монитор и USB-клавиатура. На сервере есть GeForce GT 640 и работающий VGA-вывод, так что консоль доступна; без неё переезд превращается в проблему.
2. **Статические IP гостей** (`192.168.10.60` у CT 108, `dhcp` у CT 101) — при смене подсети правятся на хосте через `pct set 108 --net0 ...` без входа в гостя.
3. **Порт-форвардинги** на новом роутере: 50607→22 (SSH), 443→192.168.10.60 (API), при необходимости 8006 (веб-интерфейс PVE).
4. **Почта уведомлений** (`postfix` → `mail-to-root`): при смене провайдера SMTP-порт 25 часто заблокирован. Уведомления бэкапов надо переводить на внешний SMTP-релей или webhook, иначе «тихий» бэкап станет действительно тихим.
5. **Физическая сохранность дисков**: ZFS-пул `infocard` уже без репликации; при перевозке это единственная копия данных VM 102/106/107 и CT 101. Диски перевозить в антистатической упаковке, перед выключением — `zpool export`/корректный shutdown, после включения — `zpool status` до запуска гостей.

## 6. Оценка времени восстановления (для нашей конфигурации)

Предусловие: интернет в новом месте уже подключён, роутер настроен, домен и DNS-панель под рукой, бэкапы свежие.

| Шаг | Время |
|---|---|
| Подключить сервер, включить, дождаться загрузки PVE | 3–5 мин |
| Локальная консоль: проверить/поправить IP `vmbr0`, `ifreload -a` | 5–15 мин (0 мин, если подсеть та же) |
| Проверить `pct list`/`qm list`, поднять CT 108 и CT 101 | 2–5 мин |
| Порт-форвардинги на роутере + проверка снаружи | 5–10 мин |
| Обновить DNS A-запись | 1–2 мин (распространение — до TTL, при 300 с ≈ 5 мин) |
| Worker Agent переподключается сам | 1–5 мин после доступности DNS |
| Проверка API, панели, очереди, бэкапа | 10–20 мин |

**Итого при публичном IPv4: 30–60 минут** простоя (совпадает с исходной оценкой).
**При CGNAT:** 1–3 дня, если заказывать статический IP у провайдера; **15–30 минут**, если заранее поднят WireGuard-туннель на VPS.
**При забытом высоком TTL DNS:** к техническому времени добавляются часы на распространение записей.

## 7. Что это меняет в плане проекта

Добавляются обязательные требования (внесены в `STATUS.md`):

1. `docs/operations/relocation-runbook.md` — чек-лист переезда, поддерживается в актуальном состоянии.
2. Конфигурация Worker Agent: адрес управляющего узла — только домен, реконнект с backoff, без ручного перезапуска.
3. Control Plane: режим обслуживания, восстановление очереди после рестарта, идемпотентность задач.
4. Cert-manager/ACME: только DNS-01.
5. Внешний SMTP или webhook для алертов.
6. Решение по VPS-точке входа — отдельный ADR (0004), до Этапа 4 (публичный API).

## 8. Открытые вопросы

- Домен платформы (кто регистрирует, где DNS, есть ли доступ к API DNS-провайдера для DNS-01).
- Нужен ли VPS-релей: если да — провайдер, регион, 1 vCPU/1 GB достаточно.
- Ожидаемый срок переезда — от него зависит, окупается ли переезд VM 104 на другой сервер раньше.
