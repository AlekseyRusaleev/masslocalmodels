# ADR 0004 — Топология хранения: что лежит на каком узле

- **Статус:** accepted (уточняет [`0001`](0001-architecture.md) §1 и §5, устраняет неоднозначность в термине «object storage»)
- **Дата:** 2026-11-05
- **Контекст:** при обсуждении VPS возник вопрос, хранит ли сервер веса моделей. В `DISTRIBUTED_AI_PLATFORM_PLAN.md` §3.1 object storage изображён внутри Control Plane, а §3.4 требует, чтобы тяжёлые данные не проходили через управляющий узел. Нужно развести «логический компонент» и «физическое место».

## 1. Веса моделей на управляющем сервере не хранятся

Это следует прямо из плана:

- §0.2 п.4: «Не размещать большие модели на управляющей VM. Она не имеет GPU и не предназначена для инференса».
- §3.4: «Тяжёлые веса, видеоданные и промежуточные тензоры не должны без необходимости проходить через Proxmox».
- §5.5: локальная структура `ComputeNetwork/models/<model>/<revision>/…` описана **на Worker**.
- §5.4: «По умолчанию участник может получать нужные файлы напрямую из исходного репозитория, а не от другого участника».

Control Plane хранит **метаданные**, а не байты весов:

| Что | Где | Размер |
|---|---|---|
| `model_catalog`, `model_revisions`, `model_artifacts` | PostgreSQL на Control Plane | килобайты на модель |
| Манифест + SHA-256 каждого файла | PostgreSQL | килобайты |
| Сам `manifest.json` и `checksums.sha256` | Worker (локальный кэш) + копия в БД | килобайты |
| Веса (`*.safetensors`) | **только Worker** | гигабайты |

Порядок по §5.3: Scheduler выбирает Worker → Worker проверяет локальный кэш и свободный диск → скачивает **сам** с источника (Hugging Face с закреплённым commit hash или наш approved artifact) → сверяет SHA-256 по манифесту → отчитывается Control Plane о готовности. Байты весов не проходят через управляющий узел.

## 2. Что реально проходит через сервер

| Поток | Объём | Комментарий |
|---|---|---|
| Запросы и ответы LLM (текст) | килобайты — единицы мегабайт на запрос | проходит через API Gateway, это нормально |
| Метаданные заданий, lease, heartbeat | байты | — |
| Пользовательские файлы, вложения | мегабайты — гигабайты | в Object Storage, не через горячий путь API |
| Видео/изображения (этап 9) | гигабайты на задачу | только через presigned URL на Object Storage, не через VPS |
| Веса моделей | гигабайты на модель | **никогда** через сервер |

Итог: «сервер только для администрирования и распределения» — верно для весов и тяжёлых данных, но не буквально: текстовый трафик инференса проходит через API Gateway, иначе невозможно ни аутентифицировать запрос, ни учесть потребление.

## 3. Object Storage: логический компонент, отдельное физическое место

В §3.1 S3-совместимое хранилище нарисовано внутри Control Plane — это **логическая** принадлежность (Control Plane выдаёт presigned URL и проверяет права), а не требование держать диски на той же машине.

Распределение по площадкам (обновлено 2026-11-05 после вывода Proxmox из плана):

| Площадка | Роль | Диск | Что размещаем |
|---|---|---|---|
| VPS, Москва (144.31.61.208) | Control Plane + файлы на старте | 120 GB (109 свободно) | PostgreSQL, NATS, Go API, веб-панели, аудит, ledger, пользовательские файлы (шифрованные). Веса — нет. |
| Worker 01 (Windows, RTX 5060) | Data Plane | `D:` 192 GB свободно | Локальный кэш весов, который он обслуживает |
| Worker 02 (RTX 3060) | Data Plane | уточнить | Локальный кэш весов |
| Домашний Proxmox | вне платформы | 663 GB thin | обслуживает только проект владельца `Infocard` |

Пользовательские файлы на этапе MVP хранятся на диске VPS в `/var/lib/compute-control/files` с шифрованием на уровне приложения. Вынос в S3/MinIO — отдельная задача, когда объём перестанет помещаться в 120 GB: интерфейс Object Storage проектируется так, чтобы смена бэкенда не меняла API (план §13.4).

## 4. Зеркало весов — опция, а не основа

S3-зеркало моделей имеет смысл только в трёх случаях:

1. источника больше нет или он недоступен из РФ;
2. лицензия прямо разрешает распространение весов, и это проверено (ADR 0001 §5);
3. парк Worker-ов вырос настолько, что внешний трафик Hugging Face стал узким местом.

Для MVP по умолчанию: **Worker качает напрямую с источника по закреплённой ревизии**, а сервер выдаёт только манифест и хеши. Поэтому 120 GB на VPS не являются ограничением для старта.

Уточнение к предыдущему обсуждению: фраза «MinIO для артефактов моделей» на Proxmox была неточной формулировкой. Proxmox нужен как узел данных для **пользовательских файлов и бэкапов**; зеркало весов — лишь необязательное расширение при выполнении трёх условий выше.

## 5. Пользовательские файлы — единственное, что требует S3 с первого дня

План §8.4, §12.1, §13.4 требует object storage для файлов проектов и вложений с presigned URL и шифрованием. Их объём несопоставим с весами (мегабайты на документ), но:

- они должны быть зашифрованы приложением (envelope encryption, ADR 0001 §6);
- они должны попадать в бэкап;
- VPS на 120 GB для них годится на старте, но при росте объёма переезжают на Proxmox/MinIO без изменения API (меняется только конфиг storage backend).

## 6. Последствия

1. VPS 4 GB RAM / 120 GB — достаточен для Control Plane; отсутствие места под веса не является блокером.
2. Proxmox после удаления VM 104 становится узлом данных: MinIO, `vzdump`, `pg_dump`. Его переезд не влияет на публичный вход платформы.
3. Worker обязан сам сообщать свободное место, скачивать возобновляемо, проверять SHA-256 и не удалять незакреплённые пользовательские файлы (план §2.3, §5.3, §5.5).
4. В `/v1/models` и в ответах API никогда не попадают пути к весам, ID Worker-ов и адреса хранилища.
