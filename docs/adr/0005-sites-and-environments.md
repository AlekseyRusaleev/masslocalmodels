# ADR 0005 — Площадки и среды: всё на арендованном VPS

- **Статус:** accepted, заменяет предыдущую редакцию от 2026-11-05 (там было prod на VPS + staging на Proxmox)
- **Контекст:** владелец вывел домашний Proxmox из плана платформы — на нём остаётся его собственный проект `Infocard`, который сейчас важнее. Все компоненты платформы разворачиваются на арендованном VPS в Москве.

## 1. Решение

| Компонент | Где | Статус |
|---|---|---|
| Control Plane (API, PostgreSQL, NATS) | VPS `144.31.61.208`, `/opt/compute-control` | **развёрнуто, версия 0.2.0** |
| TLS и публикация | nginx на том же VPS, vhost `ai-platform` | vhost включён; сертификат — после синхронизации DNS |
| Пользовательские файлы / S3 | сначала диск VPS (`/var/lib/compute-control/files`), вынос в S3 — позже | план |
| Веса моделей | **только Worker-машины** (ADR 0004) | план |
| Домашний Proxmox | **вне плана платформы**, обслуживает только `Infocard` | исключён |

## 2. Что это меняет

1. Proxmox больше не участвует: `CT 108 compute-control` остановлен (не удалён — на случай, если понадобится стенд). VM 104 `Infocard`, CT 101 и пул `infocard` платформа не затрагивает.
2. Staging как отдельная площадка исчез: при необходимости стенд делается на том же VPS отдельной базой (`compute_control_staging`) и другим портом, без второго сервера.
3. Переезд домашнего сервера на платформу не влияет вообще — публичный вход живёт в Москве.
4. Остаётся одна точка отказа: этот VPS. Компенсация — ежедневный `pg_dump` + код и конфигурация в репозитории; поднять копию на любой другой машине можно за 15–30 минут (процедура в `scripts/vps-control-plane.sh`).

## 3. Сосуществование с действующим проектом владельца

На VPS работает живой проект `nasushno` (nginx, PostgreSQL 16, Go API на `:8080`). Платформа поставлена рядом:

| Решение | Причина |
|---|---|
| PostgreSQL — существующий кластер 16, отдельные роль `control` и база `compute_control` | не ставим второй сервер БД, не трогаем `nasushno` |
| API слушает `127.0.0.1:8090` | 8080 занят `nasushno-api` |
| NATS слушает `127.0.0.1:4222` | порт свободен, наружу не публикуется |
| Отдельный vhost nginx + отдельные журналы | нулевой риск для работающего сайта |
| Отдельный бэкап `/var/backups/compute-control`, cron 03:40, 7 дней | не пересекается с бэкапом владельца в 03:17 |

Проверено: `nasushno.service` не перезапускался (тот же `ActiveEnterTimestamp`), `https://nshno.tech` и `https://nsk.nshno.tech` отвечают 200.

## 4. Аутентификация (этап 1)

| Что | Детали |
|---|---|
| Таблицы | `users`, `api_keys` (миграция `0002`), `key_hash = HMAC-SHA256(pepper, secret)` |
| Формат ключа | `dai_<key_id>.<secret>`, key_id — индекс, секрет — 32 случайных байта |
| Pepper | `/etc/compute-control/.api_pepper`, 60+ символов, вне БД |
| Endpoints | `/v1/models`, `/v1/usage` — по ключу; `/admin/v1/users`, `/admin/v1/keys` — scope `admin` |
| Администратор | `admin@nshno.tech`, токен в `/root/compute-admin-token` (chmod 600) |

Проверено на живой базе: без ключа → 401, кривой ключ → 401, неверный секрет → 401, действующий ключ → 200; ключ без scope `admin` → 403; после отзыва → 401; повторный отзыв → 404.

## 5. Ограничения

1. 4 GiB RAM делится с `nasushno` (≈0.9 GiB). Платформа сейчас занимает ~20 MB; запас есть, но при росте панелей понадобится тариф выше.
2. 120 GB диска: Control Plane и пользовательские файлы на старте; весов там нет и не будет.
3. Один узел — нет резерва. Пока это осознанный размен: дешевле и проще, ценой RTO 15–30 минут при аварии.
4. PostgreSQL 16 на prod. Если понадобится 17 — плановый `pg_dump`/restore, миграции версионно-нейтральны.
