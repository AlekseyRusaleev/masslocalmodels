# ADR 0006 — MVP на одном Worker и готовность к набору участников

- **Статус:** accepted, 2026-11-05
- **Контекст:** характеристики второго узла (RTX 3060) и будущих участников неизвестны; владелец начнёт искать людей только после того, как платформа будет собрана. Планировать этапы вокруг второй GPU нельзя — это заблокировало бы всю работу.

## 1. Решение

1. **MVP строится на одном Worker** — компьютер владельца (Windows 11, Ryzen 5 5600X, RTX 5060 8 GB). Всё, что нужно для демонстрации, должно работать на одном узле.
2. **Распределённый PoC (шардинг, pipeline, Petals) не строится и не обещается** до появления второго реального GPU. Архитектурно он остаётся (адаптеры, lease, топологии в модели данных), но реализация и замеры — после набора участников.
3. **Приоритет этапов меняется:** сначала вертикальный срез «пользователь → Control Plane → Worker → ответ модели», затем панели и onboarding, и только потом распределённые режимы.
4. **Рекрутинг возможен только при наличии трёх вещей:** рабочего демо, понятного онбординга (enrollment за одну команду) и внятных гарантий владельцу железа (пауза, лимиты, отсутствие произвольного кода).

## 2. Что это меняет в модели данных и API

Уже реализовано (этап 2, серверная часть):

| Компонент | Состояние |
|---|---|
| `worker_enrollments` | одноразовый токен, TTL 24 ч, привязка к аккаунту, HMAC-хеш в БД |
| `worker_nodes` | узел с владельцем, состоянием (`available/paused/drain/maintenance/quarantined/offline`), trust class, секретом устройства |
| `worker_capabilities` | CPU/RAM/GPU/диски/сеть как JSON, заполняется при enrollment |
| `worker_heartbeats` | история телеметрии без содержимого задач |
| `POST /admin/v1/enrollments` | выпуск токена подключения (scope `admin`) |
| `POST /worker/v1/enroll` | регистрация узла, возврат `device_token` один раз |
| `POST /worker/v1/heartbeat` | телеметрия → ответ `desired_state` и интервал |
| `GET /admin/v1/workers` | таблица узлов: GPU, VRAM, диск, последний heartbeat |
| `POST /admin/v1/workers/{id}/state` | пауза, drain, обслуживание, карантин |

Не реализовано осознанно: leases и выдача задач, топологии, планировщик, benchmark, mTLS-сертификаты устройств, `quarantine` с отзывом идентичности.

## 3. Идентичность устройства: сейчас токен, потом сертификат

Сейчас — Bearer `dai_…` с HMAC-хешем в БД (тот же механизм, что у API-ключей). Это дешево, обратимо, не требует PKI и не мешает позже перейти на mTLS: enrollment остаётся тем же, меняется только артефакт (вместо `device_token` узел получает сертификат, подписанный внутренним CA). При переходе старые токены отзываются.

Правило уже в силе: узел инициирует соединение сам и не принимает входящих подключений из интернета.

## 4. Требования к участнику (для рекрутинга)

Полный опросник — [`../operations/participant-requirements.md`](../operations/participant-requirements.md). Кратко:

| Категория | Требование |
|---|---|
| ОС | Windows 11 или Linux Ubuntu 22.04+ |
| GPU | NVIDIA, ≥8 GB VRAM (RTX 3060 и новее), рабочий драйвер, `nvidia-smi` отвечает |
| RAM | ≥16 GB |
| Диск | ≥60 GB свободно на отдельном разделе под кэш весов |
| Сеть | ≥20 Mbit/s upload, без CGNAT (или с готовностью к релею), стабильный IP |
| Время работы | ≥8 часов в сутки, готовность к паузам |
| Согласие | понимает, что GPU-узел видит входные данные приватных задач доверенного пула |

Узлы неоднородны: RTX 3060 12 GB и RTX 5060 8 GB — разные профили, CU не сравниваются напрямую без benchmark.

## 5. Что должно существовать до приглашения первого человека

1. Рабочий демо-срез: запрос в `/v1/chat/completions` уходит на реальный Worker и возвращает ответ с потоковой выдачей.
2. Онбординг: одна команда установки, enrollment, видимый статус узла в панели.
3. Гарантии владельцу железа: пауза в один клик, лимиты GPU/CPU/RAM/диска, отсутствие произвольного shell, отсутствие доступа к его файлам.
4. Публичная страница «что вы получите и что отдаёте» без обещаний, которых нет.
5. Аудит и понятная политика данных (кто видит промпты).

## 6. Последствия и риски

| Риск | Следствие | Компенсация |
|---|---|---|
| Второй GPU не появится | нет доказательств WAN-шардинга | не обещать в текстах; демонстрировать то, что работает на одном узле |
| Единственный Worker выключается | нет inference при живом API | очередь + понятная ошибка; API остаётся доступным |
| Разнородное железо у новых участников | непредсказуемая производительность | benchmark-профили и реплики вместо шардинга |
| Доверие к чужим узлам | приватные данные у постороннего | trust class `private` по умолчанию, публичные узлы только для безопасных задач |
