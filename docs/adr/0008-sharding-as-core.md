# ADR 0008 — Шардирование тяжёлых моделей как ядро продукта

- **Статус:** accepted, 2026-11-05. Уточняет и **переставляет приоритеты** [`ADR 0006`](0006-mvp-single-worker.md).
- **Контекст:** владелец уточнил суть проекта: смысл не в запуске модели на одной видеокарте (это делается локально без платформы), а в том, чтобы **делить тяжёлую модель между участниками** — тогда становятся доступны модели, которые физически не влезают в одну карту, — и **складывать вычислительные мощности** нескольких GPU.

## 1. Что это меняет

| Было в ADR 0006 | Стало |
|---|---|
| MVP = один Worker, модель на одной GPU | MVP обязан **продемонстрировать шардинг**: одна модель, слои которой живут на разных машинах |
| Этап 3B (два GPU) отложен «до появления участников» | Шардинг — **центральный этап**, а не приложение. Всё остальное готовит для него почву |
| Критерий успеха: «модель работает на моём ПК» | Критерий успеха: «модель, которая не помещается ни в одну из карт, отвечает, и её слои лежат на разных узлах» |

## 2. Честная физика: ёмкость, а не скорость

При авторегрессионной генерации каждый токен последовательно проходит все стадии. Значит время на токен ≈ сумма вычислений по стадиям + сетевые переходы между ними. Сеть добавляется к каждому токену, а не к запросу.

Оценки для нашей геометрии (базовая скорость 8B на RTX 5060 — измеренные 70 tok/s, то есть ≈14 мс на токен):

| Сценарий | Ёмкость | Добавка сети на токен | Ожидаемая скорость |
|---|---|---|---|
| 8B на одной GPU | 8 GB | 0 | **70 tok/s** (измерено) |
| 32B Q4 (~20 GB) на двух GPU, RTT 30–40 мс | 20 GB | 60–80 мс | **8–10 tok/s** |
| 32B Q4, RTT 100 мс (разные города) | 20 GB | 200 мс | **3–5 tok/s** |
| 70B Q4 (~40 GB) на трёх-пяти GPU | 40 GB | 3–5 переходов | **3–6 tok/s** |

## 2.1. Уточнение: рост скорости есть, но не там, где кажется

Формулировка «шардирование даёт ёмкость, а не скорость» верна только для **одного запроса через WAN**. План (и практика) различают три разных механизма — их нельзя смешивать, потому что от них зависит и архитектура, и что мы обещаем людям.

| Механизм | Что происходит с одной генерацией | Что происходит с суммарной скоростью сети | Где применим |
|---|---|---|---|
| **Реплики** (модель целиком на каждой карте) | не меняется (70 tok/s) | **растёт почти линейно**: N карт = N параллельных запросов | везде, где модель влезает в карту |
| **Pipeline / шардинг по слоям** (наша суть) | **замедляется**: к каждому токену добавляются сетевые переходы | растёт: пока одна последовательность идёт по стадиям, другие могут занимать освободившиеся стадии (микробатчи) | ёмкость: модель не влезает в одну карту |
| **Tensor parallel** (слой делится между картами) | **ускоряется**: матрицы считаются параллельно, ~1.3–1.8× на 2 картах | растёт | только внутри одной машины / локальной сети с NVLink/PCIe |

Отсюда три вывода, которые надо зафиксировать в продуктовых текстах:

1. **«Складывать вычислительные мощности» — да, это работает**, но через реплики и микробатчи: чем больше карт, тем больше запросов обслуживается одновременно. Именно это имел в виду план в §4.1 («лучше увеличивает суммарную пропускную способность») и §15.4 («для роста суммарной пропускной способности в первую очередь добавлять replica»).
2. **Скорость одного ответа растёт только с tensor parallel** — и только на быстром канале. Через WAN он не применяется (§4.3 плана).
3. **Шардинг по слоям через WAN — про ёмкость.** Обещание «добавили карту — стало быстрее» для него неверно, и план прямо запрещает такое обещание (§0.3: «Не обещать ускорение одного запроса при каждом добавлении GPU», §22.3: «не обязательно скорость генерации одного токена»).

Практическое следствие для платформы: нужны **два класса обслуживания**, и Scheduler обязан их различать.

| Класс | Модель | Политика | Ожидание пользователя |
|---|---|---|---|
| `fast` | 8B, целиком на одной карте | реплики, свободная карта, минимальная очередь | 40–70 tok/s, отклик как у локальной |
| `capacity` | 32B/70B, шард-группа | нужна вся группа узлов; при потере узла — деградация или отказ | 3–10 tok/s, зато модель, которой нет ни у кого по отдельности |

В карточке модели в панели показывается класс и измеренная скорость — чтобы пользователь не ждал от 70B скорости 8B.

Выводы, которые нельзя замалчивать в документации и на странице продукта:

1. **Шардинг даёт доступ к большим моделям, а не скорость.** 32B через WAN будет отвечать медленнее, чем 8B локально.
2. **Prefill (обработка промпта) страдает меньше** — он параллелится; долгий контекст будет обрабатываться приемлемо, а генерация — медленно.
3. Для «быстро поболтать» остаётся локальная 8B (реплика), для «нужна модель побольше» — шардированный пул. Это два класса обслуживания, и Scheduler должен их различать (план §4).
4. Складывание мощностей по-настоящему проявляется на **параллельных независимых запросах** (реплики + очередь), а не внутри одного запроса.

## 3. Чем делать: конкретный стек

| Вариант | Что даёт | Риск |
|---|---|---|
| **llama.cpp RPC** (`rpc-server` + `llama-server --rpc`) — выбор по умолчанию | разбиение слоёв по узлам через TCP, один GGUF, OpenAI-совместимый сервер на координаторе | нет TLS и аутентификации — только внутри WireGuard/SSH-туннеля; синхронная передача активаций |
| ggml multi-node tensor parallelism (NCCL, появился в ggml 0.29 / llama.cpp v0.9.0) | тензорный параллелизм между узлами | требует NCCL и быстрой сети; для WAN не подходит, интересен для узлов в одной локалке |
| Petals | публичный WAN-шардинг, устойчивость к уходу узлов | **проверено 2026-11-06, не годится:** только bloom/falcon/llama/mixtral (Qwen3 невозможен, пинит `transformers <4.35`), последний релиз 2023-11-20, не ставится на Python 3.12 — подробно [STATUS §3.28](../STATUS.md#328-спайк-petals-не-годится-2026-11-06-день) |
| vLLM pipeline parallel | зрелый serving | требует NVLink/IB; для дома и WAN не вариант |
| Собственный pipeline на `torch.distributed.pipelining` | полный контроль | Alpha API, много своей работы — оставить как резерв |

Решение: **llama.cpp RPC как основной механизм**, NCCL-TP — для узлов в одной локальной сети, Petals — как эксперимент, не как фундамент. Слой абстракции `runtime adapter` остаётся: Control Plane не знает, RPC там или vLLM.

> **Уточнение (2026-11-06).** Petals проверен и отпал ([`STATUS §3.28`](../STATUS-archive.md#328-спайк-petals-не-годится-2026-11-06-день)): он умеет только bloom/falcon/llama/mixtral, пиннит `transformers <4.35` и не ставится на Python 3.12. Основной механизм на сегодня — llama.cpp RPC, но у него остаётся зависимость от отдачи координатора (веса идут через него). Поэтому **пишется свой рантайм пайплайна слоёв**: узел держит свои блоки, между узлами идут активации. Цель первого демо — **GPT-OSS-120B** (Apache 2.0, 5.1B активных из 117B): разреженность даёт и ёмкость, и скорость, а лицензия не мешает росту сети.

Бинарники уже есть в официальных сборках: `llama-b12110-bin-win-cuda-13.4-x64.zip` (Windows, CUDA 13.4) и `llama-b12110-bin-ubuntu-x64.tar.gz` (Linux, CPU). Наличие `rpc-server` в архивах проверяется при первом запуске.

## 4. Безопасность шардинга

`rpc-server` не имеет ни TLS, ни авторизации: любой, кто дотянется до порта, получит доступ к слоям и сможет подсунуть свои активации. Поэтому:

1. Порт слушается **только** на интерфейсе WireGuard (или SSH-туннеля), никогда на публичном.
2. Узел-координатор аутентифицируется на Control Plane своим device token, а туннель поднимает сам (исходящее соединение) — как в ADR 0003.
3. Каждый узел видит только свои слои и активации, но не весь KV-кэш других сессий; межпользовательское переиспользование KV выключено (план §13.5).

| 3 | Шардинг **через WAN** (GPU дома + CPU-узел на VPS через SSH-туннель) | ответ приходит, замерены tok/s и вклад сети | **механизм готов, скорость упирается в канал.** Туннель через платформу работает: кадры с идентификатором соединения, RPC стартует и грузит слои. Измерено 1.3–1.4 MB/s в каждую сторону — это предел домашней отдачи, поэтому первая загрузка удалённой стадии занимает десятки минут. Дальше: кэш тензоров на стадии (`-c`, включён) и доставка весов до узлов ([STATUS §3.27](../STATUS.md#327-туннель-заработал-rpc-идёт-через-платформу-узкое-место-канал-2026-11-06-день)) |
| 4 | Шардинг **двух GPU** (RTX 5060 + будущая RTX 3060) | модель 20 GB, которая не влезает ни в одну карту, отвечает | ждёт второй узел |
| 5 | Устойчивость: уход узла посреди генерации | запрос завершается контролируемой ошибкой, lease возвращается в очередь | не начато |

## 5.2. WAN-проверка 2026-11-05: узкое место — доставка весов, а не сеть

Схема: GPU-узел на машине владельца + CPU-узел на VPS (`ggml-rpc-server`, 2 потока), связь через SSH-туннель (`tools/ssh_tunnel.py`, порт 50053 на VPS слушает только loopback).

| Измерение | Значение |
|---|---|
| RTT до VPS (TCP handshake 22/tcp) | **10 мс** — канал оказался лучше, чем ожидалось |
| Базлайн loopback: GPU + CPU-узел (2 потока), сплит 75/25 | 120 токенов / 2.1 с = **56.7 tok/s** |
| Сплит 25 % на VPS через WAN: загрузка весов | **> 25 минут и не завершилась**, RSS узла дошёл до 1.17 GB из ~1.2 GB |
| Скорость передачи весов через туннель | **≈1.5 MB/s** (≈12 Mbit/s) |

Вывод, который меняет реализацию: **веса нельзя передавать от координатора к узлу по WAN**. Загрузка 1.2 GB заняла больше 25 минут — это 12 Mbit/s, то есть упирается в upload домашнего канала, а не в RPC. Для 32B-модели (20 GB) такой путь вообще неприемлем.

Правильно — как и записано в плане (§5.3–5.5): каждый узел скачивает **только свой диапазон слоёв напрямую** из источника (HuggingFace по закреплённой ревизии или S3) на своей скорости, параллельно с другими, а координатор передаёт лишь манифест с хешами. Это надо реализовать до шага 4; иначе холодный старт шард-группы будет измеряться десятками минут.

Что осталось неизмеримым: цена одного WAN-перехода на токен. Померить не удалось, потому что модель не догрузилась. Оценка по RTT: 2 перехода × 10 мс = 20 мс на токен; при 32B на двух GPU с ~28 мс вычислений это ≈21 tok/s. Оценка помечена как оценка и будет заменена измерением после реализации прямой загрузки шардов.

Побочные наблюдения:

1. SSH-туннель как транспорт RPC работает без нареканий (порт на VPS не публикуется — слушает только `127.0.0.1`).
2. Туннель поднимается за секунды и держит соединение; пропускная способность ограничена upload, а не SSH.
3. CPU-узел на 2 потоках Xeon E5-2699 v4 отдаёт ~56 tok/s вместе с GPU при 25 % слоёв — то есть слабый, но не бесполезный узел.

## 5.4. Прямая загрузка артефактов (реализовано 2026-11-05)

Вывод из §5.2: вес не должен идти через координатор. Реализовано в агенте:

| Что | Где |
|---|---|
| Загрузчик | `internal/download` — Range-докачка, SHA-256, атомарная замена, повторы |
| Многопоточность | `parallel.go` — N диапазонов одновременно, склейка по порядку, уборка частей при ошибке |
| Команда | `worker-agent fetch --url ... --dest ... [--sha256 hex] [--streams 8]` |
| Тесты | 6 тестов: проверка хеша, отказ при неверном хеше, докачка с `.part`, параллельная склейка, fallback когда сервер игнорирует Range, разбор размера |

Измерения скорости с Hugging Face (файл `model-00001-of-00005.safetensors`, Qwen3-8B):

| Режим | Скорость |
|---|---|
| Один поток | **1,59–1,60 MB/s** |
| 6 параллельных диапазонов (curl) | **10,45 MB/s** — в 6,6 раза быстрее |
| 4 потока нашим загрузчиком сразу после серии тестов | 3,22 MB/s |

Выводы:

1. **Параллельные диапазоны обязательны.** Один поток с HF — 2 МБ/с, что для 20 GB модели означает почти три часа.
2. **Провайдер троттлит.** После нескольких сотен мегабайт скорость падает (10,45 → 3,22 MB/s), поэтому число потоков — настраиваемый параметр, а докачка и повторы обязательны.
3. **Локальный кэш RPC-ноды (`-c`) проблему не решает**: загрузка модели 12,1 с на «холодную» и 10,0 с на «тёплую» — разница в пределах шума, кэш занял 1 650 MB, но координатор всё равно отдаёт тензоры.
4. Проверка хеша работает на реальном файле: неверный SHA-256 даёт отказ, файл не остаётся на диске; верный — сохраняется.

Что осталось: связать `fetch` с манифестом модели в Control Plane (этап 6), чтобы узел получал список файлов, их хеши и диапазон слоёв, а не отдельные команды вручную.

## 5.5. Что измерено 2026-11-05 (шаг 2, loopback)

Сборка `llama-b12110-bin-win-cuda-13.4-x64` + `cudart-...-cuda-13.4-x64`, модель — GGUF `qwen3:8b` (тот же файл, что скачала Ollama), оба узла на loopback.

| Тест | Конфигурация | Результат |
|---|---|---|
| A | все слои на одном GPU-узле | 120 токенов / 2.0 с = **59.8 tok/s** |
| B | GPU-узел 62 % + CPU-узел 38 % | 120 токенов / 2.1 с = **56.9 tok/s** (−5 %) |
| C | B + длинный промпт (530 токенов) | prefill **385 tok/s**, генерация 46.5 tok/s |
| D | все слои на одном CPU-узле | 64 токена / 10.3 с = **6.2 tok/s** |

Главный вывод из A против B: **разделение слоёв само по себе почти ничего не стоит** — потеря 5 % на loopback, где RTT ≈ 0.1 мс. Значит задержку добавляет не шардинг, а **сеть**: при RTT 30–40 мс и двух переходах на токен к 17 мс вычислений добавляется 60–80 мс, и 59.8 tok/s превращаются в ~11 tok/s. Это арифметика, а не мнение.

Вывод из D: медленный узел в группе тянет всю группу — CPU-узел с 4 потоками даёт 6.2 tok/s, и Scheduler обязан учитывать производительность каждого узла, а не только объём VRAM.

Оба прогона — через OpenAI-совместимый `/v1/chat/completions` на llama-server, то есть тем же контрактом, что будет у платформы.

Что это **не** доказывает: поведение через интернет (все узлы были на loopback), работу с моделями больше 8 GB и устойчивость к обрывам. Это шаги 3–5.

Замечания по эксплуатации:

1. `ggml-rpc-server` на Windows падает с `No devices found`, если рядом нет CUDA-рантайма: нужен архив `cudart-...-win-cuda-13.4-x64.zip`, обычного `bin-win-cuda` недостаточно.
2. Порт по умолчанию 50052, `llama-server` по умолчанию 8080 — на машине владельца занят посторонним приложением, использовали 18081/18082/18091/18092.
3. RPC-нода завершает работу, когда клиент отключается без активных задач: координатор должен переподключаться, а не считать узел мёртвым сразу.
4. Qwen3 в режиме «thinking» может потратить весь `max_tokens` на рассуждение и вернуть пустой `content`. Для панели и API это надо учитывать: либо увеличивать лимит, либо передавать шаблон без thinking.

## 6. Целевые модели

| Класс | Размер Q4 | Куда влезает | Что это даёт |
|---|---|---|---|
| 8B (Qwen3-8B) | ~5 GB | одна карта 8 GB | быстрый чат, реплики |
| 14B | ~9 GB | 8 GB + второй узел (1–2 GB) | первый настоящий шардинг |
| **32B** | ~20 GB | 8 GB + 12 GB (RTX 3060) | **флагман: ни одна из карт не тянет в одиночку** |
| 70B | ~40 GB | 3–5 узлов | демонстрация масштаба, скорость 3–6 tok/s |

Флагман для показа людям — **32B на двух узлах**: это ровно тот случай, который владелец назвал смыслом проекта, и его нельзя воспроизвести на одной карте.

## 7. Последствия для остальных этапов

1. **Control Plane** обязан хранить топологию: какой узел держит какие слои, кто координатор, какая версия модели. Это `topologies`/`topology_stages` из плана §19 — их проектирование переходит из «потом» в следующий этап.
2. **API** остаётся прежним (`/v1/chat/completions`): клиент не знает, что модель размазана по трём домам.
3. **Scheduler** получает два класса политик: реплика (быстро, любая свободная GPU) и шард-группа (нужны все узлы группы, иначе деградация).
4. **Загрузка весов** становится частичной: узел скачивает только свой диапазон слоёв — это и есть ответ на «позволяя их в принципе скачать».
5. **Панель** получает экран топологии (какие слои где), но не раньше, чем появится реальная топология.
