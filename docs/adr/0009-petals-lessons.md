# ADR 0009 — Что берём у Petals и что нет

- **Статус:** accepted как ориентир архитектуры, 2026-11-05
- **Источник:** [bigscience-workshop/petals](https://github.com/bigscience-workshop/petals), статьи [arXiv:2209.01188](https://arxiv.org/abs/2209.01188) и [arXiv:2312.08361](https://arxiv.org/abs/2312.08361)
- **Контекст:** [`ADR 0008`](0008-sharding-as-core.md). Наш первый путь — llama.cpp RPC, где координатор держит весь GGUF и **передаёт тензоры узлам**. Измерение показало, что это узкое место: 1.2 GB шло по домашнему каналу более 25 минут.

## 1. Главная идея, которую надо перенять

Petals строит шардирование **снизу**: каждый сервер держит только свои блоки и сам их скачивает, а клиент ведёт пайплайн блок за блоком. Координатор не обязан иметь модель целиком.

| | llama.cpp RPC (наш PoC) | Petals (блоки как сервис) |
|---|---|---|
| Кто держит веса | координатор целиком + копии тензоров на узлах | каждый узел только свой диапазон блоков |
| Кто качает веса | координатор, затем передаёт по сети | узел сам, параллельно, со своего канала |
| Нужен ли полный файл модели у кого-то | да | нет |
| Что делает координатор | грузит модель и раздаёт тензоры | последовательно вызывает блоки |

Это ровно то, чего требует владелец («позволить скачать модели, которые иначе не поднять») и что мы не смогли получить на RPC. Вывод: **блочная модель Petals — целевая архитектура**, RPC остаётся быстрым способом проверить транспорт.

## 2. Что берём конкретно

1. **Блочное шардирование по слоям** с упаковкой в отдельные артефакты: узел получает манифест «слои 12–23» и качает только их (у нас уже есть `model_artifacts` + `manifest`, не хватает разбиения по слоям).
2. **Клиентский пайплайн**: координатор не грузит модель, а идёт по стадиям. У нас это ложится на `topologies`/`topology_stages` — они уже реализованы.
3. **Устойчивость к уходу узла**: если блок недоступен, запрос перенаправляется на другую реплику этого блока. У нас пока нет реплик — заложить в Scheduler.
4. **Публичный монитор состояния** (`health.petals.dev`): видно, какие блоки кто обслуживает. Наш аналог — панель узлов; стоит добавить «кто какие слои держит» и uptime.
5. **Признание вклада**: Petals показывает имена участников, отдавших ≥10 блоков. Дешёвый и работающий социальный механизм для рекрутинга — добавить в кабинет участника.
6. **Приватный swarm** для доверенного круга — совпадает с нашими trust classes, только у нас изоляция на уровне пула.
7. **Никакого произвольного кода на хосте**: сервер принимает только прямой проход по своим блокам. Это же правило уже в наших требованиях к Worker.
8. **Квантование (8-bit) ради влезания блоков** — у нас уже есть Q4 GGUF, но для блоков понадобится согласование квантования между стадиями.
9. **Docker-образ и гайд для Windows/WSL**: у Petals это `docker run ... learningathome/petals`; у нас `scripts/install-worker-agent.ps1` + README, но без контейнера и без WSL-инструкции — добавить, когда появится рантайм-адаптер.

## 3. Что не берём

1. **DHT и публичный swarm по умолчанию.** Открытая сеть без доверия не подходит для приватных чатов; публичный режим — только отдельным классом задач (план §13.2).
2. **Зависимости 2023 года.** Petals привязан к старым PyTorch/CUDA; для RTX 5060 (SM 12.0) и CUDA 13.4 совместимость надо проверять отдельно и в изолированном окружении, а не тянуть как основу.
3. **Python как единственный путь установки.** Наш первый пользователь — Windows-геймер; Go-агент без окружения остаётся приоритетом.
4. **Отсутствие учёта вклада.** У Petals нет CU/fair-share — у нас это обязательная часть (план §14).

## 4. Что из этого следует технически

1. **Реализовано 2026-11-05:** артефакты получили диапазон слоёв (`0006_artifact_layers`), узел в манифесте видит только файлы своего этапа плюс общие. Проверено: узел со слоями 0–17 не получает файл слоёв 18–35.
2. **Реализовано 2026-11-05:** карта слоёв GGUF (`internal/gguf`, команда `worker-agent gguf`). Разбор реального `qwen3-8b` (GGUF v3): архитектура `qwen3`, 36 слоёв, 399 тензоров, заголовок 5,68 MB, вес тензоров 4,86 GB. Служебные тензоры: `token_embd` 333 MB, `output.weight` 486 MB, `output_norm` 0,02 MB. Предложение разбиения на 3 части: слои 0–11 (1,35 GB), 12–24 (1,45 GB), 25–35 (1,26 GB).
3. **Важное ограничение честности:** llama.cpp RPC по-прежнему требует **весь GGUF у координатора** — он читает файл целиком и передаёт тензоры узлам. Поэтому разбиение само по себе не ускоряет загрузку RPC-группы. Оно нужно для двух других вещей: (а) гранулярная выдача артефактов узлам, (б) будущий блочный рантайм, где каждый узел держит свой файл и обслуживает свой диапазон слоёв.
4. **Служебные тензоры дорогие:** `token_embd` и `output` вместе 820 MB. При блочном рантайме их нельзя дублировать на каждом узле — `token_embd` логично оставлять первой стадии, `output` — последней. Это надо учесть в раскладке при публикации ревизии.
5. Проверить Petals как **изолированный адаптер** (Docker, отдельный venv) на одной модели: если он заводится на Blackwell — получим готовый механизм блоков и устойчивости, не изобретая свой.
6. Оценки Petals калибруют ожидания: 70B — около 6 tok/s, 180B — около 4 tok/s в публичном swarm через континенты. Наши расчёты для двух домашних GPU в одном городе (RTT 10 мс) дают 13–20 tok/s для 32B — это не противоречие, а разная геометрия.

## 5. Про скорость: что реально её поднимает

| Приём | Эффект | Применимость у нас |
|---|---|---|
| Меньше стадий с большей VRAM (2 узла вместо 4–5) | каждый переход RTT исчезает | да, при 8 + 12 GB |
| Узлы в одном городе / с низким RTT | 10 мс вместо 100 мс — в разы | да, основной рычаг |
| Реплики для быстрого класса (8B целиком) | 40–70 tok/s | да, уже есть |
| Speculative decoding (draft-модель рядом) | 1,5–2× на декоде | проверить на llama.cpp |
| Батчинг и микробатчи | суммарная скорость растёт, одиночная — нет | этап 7 |
| Квантование Q4/Q5 | влезает больше слоёв на карту | уже используется |

Честная граница: одиночный запрос через WAN не может быть быстрее локальной карты — сеть добавляется к каждому токену. Платформа продаёт не «быстрее», а «модель, которой у тебя нет» плюс суммарную пропускную способность.
