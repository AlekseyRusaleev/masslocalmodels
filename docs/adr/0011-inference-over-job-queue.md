# ADR 0011 — Инференс через очередь заданий, а не через входящие соединения

**Дата:** 2026-11-05
**Статус:** принято
**Контекст этапа:** 4 (public API `/v1/chat/completions`)

## 1. Проблема

Узлы участников находятся за NAT и в мобильных сетях: у них нет публичного адреса, портов и стабильного TLS-сертификата. Пользователь при этом ждёт обычный OpenAI-совместимый поток токенов.

Классические варианты не подходят:

| Вариант | Почему нет |
|---|---|
| Обратный прокси к узлу | нет входящего адреса; проброс портов у частника не поддерживается |
| WireGuard-оверлей | работоспособно, но участник получает доступ в сеть платформы — лишняя поверхность атаки и поддержка |
| Тоннель на каждого участника | сложность на стороне сервера, узкое место по числу сокетов |
| Только pull-модель без стрима | пользователь ждёт весь ответ целиком |

## 2. Решение

Пользовательский запрос превращается в **задание** в PostgreSQL. Узел забирает его сам.

```
клиент ──POST /v1/chat/completions──▶ Control Plane ──INSERT jobs──▶ PostgreSQL
                                            ▲                            │
                                            │                     long-poll pull
                                            │                            ▼
                              чанки (POST /chunk) ◀────────────  worker-agent
                                            │                            │
                                       SSE ▼                       локальный рантайм
                                          клиент                       (Ollama)
```

| Элемент | Решение |
|---|---|
| Очередь | таблица `jobs` (`queued → claimed → streaming → done/failed`) |
| Доставка задания | long-poll 25 с, один запрос на узел; узлы в `paused`/`drain` не получают заданий — фильтр в SQL, не на клиенте |
| Доставка ответа | поток чанков одним запросом: `POST /worker/v1/jobs/{id}/chunkstream`, тело в формате NDJSON (по объекту на чанк) |
| Выдача клиенту | SSE, `text/event-stream`, без буферизации в nginx (`proxy_buffering off`) |
| Счётчики | узел присылает `prompt_tokens`, `completion_tokens`, `eval_ms`, `finish_reason` из рантайма |
| Незнакомая модель | `404 model_not_served` сразу, а не ожидание таймаута |
| Состояние | хранится в БД, поэтому переживает рестарт API |

## 3. Следствия

**Хорошо**

- Узлу не нужен входящий порт: только исходящий HTTPS.
- Задание не теряется при падении управляющего процесса.
- Стрим идёт по тому же соединению, что и запрос — nginx справляется без настройки WebSocket.
- Счётчики токенов честные: их считает рантайм на видеокарте, а не Control Plane.
- Стоимость транспорта нулевая по сравнению с генерацией: измерено 70.5 tok/s через платформу против 70.4 tok/s напрямую, накладные расходы 25 мс на 411 чанков.

**Плохо / ограничения**

- Один узел выполняет одно задание: параллелизм появится вместе с очередью приоритетов.
- Полинг держит соединение; при тысячах узлов потребуется отдельный транспорт (NATS уже установлен, но пока не используется для заданий).
- Поток чанков требует отключённой буферизации тела запроса в nginx (`proxy_request_buffering off`); при обычной настройке прокси ответ соберётся целиком и стрим потеряет смысл.

### 3.1. Отдельный вызов на чанк — почему отказались

Первая версия отправляла каждый чанк отдельным `POST`. На бумаге это проще, на практике — катастрофа: 411 чанков × RTT 50–280 мс дали 22 секунды доставки при 5.9 секундах генерации. Пользователь видел ответ в четыре раза медленнее, чем его считала видеокарта. Поток в теле одного запроса убирает это полностью: 411 чанков доставлены за 25 мс поверх генерации. Отдельный endpoint `/chunk` оставлен для отладки.

## 4. Что не решено этим ADR

- **Шардирование между узлами** (этап 3B, [`ADR 0008`](0008-sharding-as-core.md)). Задание сейчас выполняется целиком на одном узле.
- Авторизация пользователей: задания создаются ключом со scope `chat:write`, аккаунты и история чатов — этап 5.
- Ограничение скорости и квоты на пользователя.
