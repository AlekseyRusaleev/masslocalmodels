# ADR 0012 — Вход в панель по паролю и сессиям

**Дата:** 2026-11-05
**Статус:** принято
**Контекст этапа:** 4+ (панель управления сетью)

## 1. Проблема

Панель управлялась административным API-ключом, который человек вставлял в поле
«Ключ доступа»: ключ лежал в `localStorage`, жил бессрочно и давал весь набор
прав сразу. Отсюда три следствия:

| Следствие | Почему это плохо |
|---|---|
| Нет понятия «кто это» | в журнале видно только отпечаток ключа, а не человека |
| Нет отзыва на время | ключ либо есть, либо его нет; «выйти на другом компьютере» невозможно |
| Нет разделения ролей | участнику, которому нужен только чат, приходилось давать `admin` |

Плюс ключ нельзя было задать иначе как командой на сервере: у нового человека не
было способа войти, не получив ключ с полными правами.

## 2. Решение

**Вход по email и паролю; панель работает по сессии.**

```
браузер ──POST /v1/auth/login {email,password}──▶ Control Plane
                                                    │ bcrypt.CompareHashAndPassword
                                                    │ auth_sessions INSERT (HMAC-хеш секрета)
        ◀──{token: "ses_<key_id>.<secret>", expires_at}──┘

браузер ──Authorization: Bearer ses_…──▶ любой /v1/* или /admin/v1/*
                                            │ auth.ParseAny → KindSession
                                            │ auth_sessions + users.status
                                            └─ scope из роли
```

Что зафиксировано:

| Решение | Обоснование |
|---|---|
| Пароль — bcrypt cost 12, не Argon2 | `golang.org/x/crypto` уже в зависимостях; bcrypt достаточно и переносим между сборками |
| Сессия — та же форма, что API-ключ (`key_id.secret`), но префикс `ses_` | один разбор `ParseAny`, один способ сравнить секрет постоянным временем, разные таблицы |
| Хранение — только `HMAC-SHA256(pepper, secret)` | дамп БД не даёт войти: pepper лежит в окружении сервиса |
| Срок жизни 7 суток | вход не должен превращаться в ежедневный ритуал; отзыв — одна кнопка |
| Токен в `localStorage`, не cookie | cookie потребовали бы CSRF-защиты и `SameSite`-политики на том же хосте; панель и API живут на одном origin |
| Роли `admin` и `user` | участнику не нужны узлы, топологии и задания — это чужие машины |
| Смена пароля отзывает все сессии и сразу выдаёт новую | иначе человек выкидывает сам себя, а «старые входы» остаются живыми |
| Счётчик неудач в памяти процесса | без него перебор не ограничен вовсе; общее хранилище попыток требует ещё одной таблицы и замедляет вход |

## 3. Что осталось у ключей

Ключи `dai_…` не отменяются: они остаются для программ — харнеса участника,
агента узла, скриптов. Правило простое: **человек входит паролем, программа —
ключом**. Обе схемы проверяются одним обработчиком, поэтому права и ответы
одинаковые.

## 4. Отвергнутые варианты

| Вариант | Почему нет |
|---|---|
| OIDC/внешний провайдер | лишняя зависимость для сети из нескольких человек; вернётся при наборе участников |
| JWT вместо записи в БД | нельзя отозвать по-настоящему: только по сроку; «выйти» перестаёт работать |
| Cookie-сессия + CSRF-токен | две формы защиты вместо одной; при одном origin выигрыша нет |
| Пароль в аргументе `set-password` по умолчанию | аргументы остаются в истории оболочки; поэтому читаем из stdin, если не передан явно |

## 5. Последствия

- Панель требует bootstrap: `bootstrap-admin` (ключ + аккаунт) и `set-password`
  (пароль). Без пароля вход невозможен — это проверяется явной ошибкой
  `password_not_set`, а не молчаливым отказом.
- Пароль восстанавливается только администратором сервера: почтовой рассылки
  нет, и это осознанно — SMTP на VPS не настроен.
- Перебор ограничен на процесс: после перезапуска сервиса счётчик обнуляется.
  Для сети из нескольких участников этого достаточно; общее хранилище попыток
  появится вместе с публичной регистрацией.
- Активные входы видны человеку в «Настройках»: устройство, время последнего
  запроса, срок. Это дешёвая и понятная замена «списку устройств» в больших
  сервисах.
