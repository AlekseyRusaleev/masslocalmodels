# Харнес как клиент платформы

Платформа отдаёт OpenAI-совместимый API, поэтому DeepSeek Harness может работать
через неё как через обычного провайдера: запросы уходят на VPS, задание забирает
узел участника, токены считает рантайм на видеокарте.

## Что настроено

| Что | Где |
|---|---|
| Маршрут провайдера | `%APPDATA%\DeepSeekHarness\data\settings.yaml`, секция `llm-pi-ai.providers.compute-network` |
| Секрет | `%APPDATA%\DeepSeekHarness\data\.credentials.yaml`, `refs.COMPUTE_NETWORK_API_KEY` |
| Разрешение для субагентов | там же, `subagent-model-selection.allowedModels` |
| Ключ API | выпущен командой `api-gateway issue-key admin@nshno.tech "chat:write,models:read" deepseek-harness` — без прав администратора |

```yaml
llm-pi-ai:
  providers:
    compute-network:
      displayName: Compute Network (свои GPU)
      api: openai-completions
      baseURL: https://api.nshno.tech/v1
      apiKeyEnv: COMPUTE_NETWORK_API_KEY
      defaultContextWindow: 16384
      defaultMaxTokens: 4096
      models:
        - id: "qwen3:8b"
          name: "Qwen3 8B (RTX 5060)"
          contextWindow: 16384
          maxTokens: 4096
          inputModalities: [text]
```

Настройки применяются без перезапуска: провайдер виден в панели харнеса в
«Настройки → Модели» как **Compute Network (свои GPU)**.

## Как проверить, что работает

Клиент харнеса — библиотека `@earendil-works/pi-ai`. Проверять нужно именно ей,
а не curl: она строит запрос и разбирает поток так же, как продукт.

```powershell
# один ход: должен прийти вызов инструмента
node tools/pi_ai_smoke.mjs dai_...

# полный цикл агента: вызов → результат инструмента → ответ словами
node tools/pi_ai_tool_loop.mjs dai_...
```

Результат последнего прогона:

```
шаг 1 — stopReason: toolUse | инструмент: get_weather({"city":"Москва"})
шаг 2 — stopReason: stop
ответ клиенту: Погода в Москве сейчас: температура -3°C, идет снег.
usage: {"input":191,"output":162,"totalTokens":353,...}
```

## Что платформа умеет для агента

| Возможность | Состояние |
|---|---|
| `tools` в запросе | передаются в рантайм как есть (OpenAI-схема) |
| `tool_calls` в ответе | `finish_reason: "tool_calls"`, аргументы строкой JSON, стабильные `id` |
| `tool_calls` в потоке | `delta.tool_calls` с `index` — как у OpenAI |
| История с результатами инструментов | роли `assistant` (с `tool_calls`) и `tool` принимаются, аргументы конвертируются в объект для рантайма |
| `content` массивом частей | текстовые части склеиваются; изображения отклоняются явной ошибкой |
| Окно контекста | 16384 для всех запросов: с квантованным KV-кэшом 16K целиком в VRAM (проверено на 8 GB, [STATUS §3.12](../STATUS.md#312-окно-контекста-на-8-гб-квантованный-kv-кэш-2026-11-05-ночь)) |
| Счётчики | `usage` с `prompt_tokens`, `completion_tokens`, `total_tokens` из рантайма |
| Неизвестная модель | `404 model_not_served` сразу, со списком доступного |

## Чего ждать по скорости

| Режим | Скорость | Почему |
|---|---|---|
| Чат | ~65–70 tok/s | окно 16K, вся модель в VRAM (KV-кэш `q4_0` на 8 ГБ, `q8_0` от 12 ГБ) |
| Запрос агента с инструментами | ~65 tok/s | то же окно: инструменты в него влезают |
| Промпт больше 16K | ошибка | узел отказывает вместо тихой обрезки истории |
| Первый запрос после простоя | +5–15 с | загрузка модели в VRAM; дальше она держится 30 минут (`keep_alive`) |

Окно у всех запросов одно — 16384. Меньше ставить нет смысла: с квантованным
KV-кэшом 16K работает с той же скоростью, что 4K. Больше — узел на 8 ГБ
начинает считать часть слоёв на CPU и падает до 20 tok/s.

Второй запрос во время ответа не ускоряется и не падает: на 8 ГБ стоит
`OLLAMA_NUM_PARALLEL=1`, поэтому он ждёт в очереди. Клиенты, которые шлют два
запроса сразу (OpenCode — чат и заголовок сессии), получают оба ответа по
очереди. Без этой настройки Ollama поднимает второй `llama-server`, и оба
падают на `cudaMalloc` ([STATUS §3.23](../STATUS.md#323-почему-падал-узел-под-opencode-два-раннера-и-kv-кэш-2026-11-06-день)).

## Ограничения, о которых нужно знать

1. **Политика моделей сессии фиксируется при её старте.** `subagent-model-selection`
   запоминает список разрешённых моделей в момент создания сессии, поэтому уже
   открытый чат не увидит новый маршрут. Нужен новый чат.
2. **Выбор модели в композере показывает только официальные маршруты.** Провайдер
   виден в настройках и работает по своему provider/model, но в списке композера
   этого сборки его нет. Запускать на GPU можно (а) субагентов через разрешённую
   пару провайдер/модель, (б) главного агента, если прописать его модель в
   `agent-default-model` — новый чат поднимется уже на узле.
3. **Изображения не поддерживаются** — вернётся `400` с понятным текстом.
4. **Биллинг в харнесе нулевой** — стоимость в `usage` приходит нулевая, потому
   что у платформы нет цен; счётчики токенов при этом настоящие.

## Что бывает при сбоях

| Симптом | Причина | Что делать |
|---|---|---|
| `MISSING_CREDENTIAL` | в `refs` нет `COMPUTE_NETWORK_API_KEY` | добавить ключ в `.credentials.yaml` |
| `404 model_not_served` | узел не прислал heartbeat с этой моделью | проверить `compute-node status` и `ollama ps` на машине |
| Ответ обрывается на середине | окно контекста заполнено | в журнале узла будет `context window is full` |
| `502` в потоке | nginx или api-gateway перезапускались | повторить запрос |
